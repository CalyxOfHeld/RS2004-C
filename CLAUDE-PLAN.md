# Claude autonomous plan — 2004scape C Rewrite

Prepared 2026-10-21. Proposed successor to the execution sections of `AUTONOMOUS_PLAN.md`; its objective, source rules and evidence standard stay in force. `AGENT.md` ground rules are unchanged.

## Why a new plan

`AUTONOMOUS_PLAN.md` describes the destination well. Its execution loop, though, depends on a person or a live server confirming each result, and the ledgers it produced were written by earlier models grading their own work. To work for long stretches without supervision, I need two things that don't exist yet:

1. **An objective measure of correctness** that I can run thousands of times without the user or a live server.
2. **A foundation I've verified myself**, rather than one I trust because the handoffs say so.

### What a first look already turned up

- **The 3D renderer is not a port.**
  - `src/gfx/pix3d.c` is 451 lines against Java's 2,494. `src/dash3d/world3d.c` is 406 lines against `World3D.java`'s 2,424.
  - The native renderer uses a double-precision depth buffer with a 64-ULP tolerance. The original is an integer painter's-algorithm rasterizer that relies on World3D tile ordering, occluders and `Model.draw` depth sorting.
  - Every open visual gate in the handoffs follows from this one architectural deviation: roofs, occluders, texture/palette parity, setBridge traversal, flicker and "whole-scene parity not claimed". These are not separate bugs. Patching them one at a time will never reach bit-for-bit parity.
- **The reference harness corrupts its own source.** `verification/completion/reference/isolation.patch` re-encodes `client.CHARSET` (`£` becomes `Â£`). Any oracle built from that patch has a wrong charset, which affects chat and text input comparisons.
- **The capability matrix is stale.** `capabilities.md` still lists zone packets as missing and the NPC opcode as wrong, while later handoffs say those are fixed. Neither claim has been re-checked.
- **Test strength varies.** Of 53 test programs, 18 compare against a Java oracle or a recorded fixture. The rest check native code against its own assumptions; at least `test_net_sync` sets the expected state directly.
- **An `OSRS/` directory sits in the workspace root.** It is a forbidden source and will stay unread.
- **Git is unusable as a safety net.** The repository has no commits, all 86 entries are untracked, and `.git` is owned by another Windows account (`CodexSandboxOffline`), so plain `git` refuses to run. Checkpoints have been zip files instead (over 30 in the root).
- **The server is still running.** PID 2352 (`bun.exe`) is listening on 43595, 8889 and 8899.

## Principle: the Java client is the oracle, run it, don't just read it

The bundled revision-225 client compiles and runs (JDK 8 is installed, and 18 oracles already work). Wherever a behavior can be executed, correctness means **the same input produces the same output** in Java and C. Prose ledgers become summaries of measured results, not the source of truth.

## Phase A — Foundation trust audit

Goal: know what is actually correct before building on it. This phase is read-only on gameplay code.

1. **Fix the reference harness.** Regenerate `isolation.patch` byte-safely so that the only differences are the intended hooks. Rebuild the reference classes, then re-run every existing oracle and check that its fixtures still match. Any fixture that changes is a finding.
2. **Grade every test.** Classify each of the 53 programs:
   - **A — oracle:** Java output, produced from unchanged source, compared exactly.
   - **B — real data:** cache data or the server's wire format, checked against independent expectations.
   - **C — self-referential:** expected values written from the C implementation's own assumptions.

   Class C tests stay in place but count for nothing toward parity.
3. **Build a coverage map of `client.java`.** Map every method and packet handler in `client.java` (11,105 lines) and the jagex2 classes to its C counterpart or to "absent". Result: `verification/completion/coverage-map.md`, generated by a script and re-runnable.
4. **Re-check ledger claims.** Test each "done" claim in the handoffs against the code and the coverage map. Record confirmed / refuted / unverifiable.

Exit: a coverage map plus a list of findings. Every later phase is chosen from these numbers, not from the handoffs.

## Phase B — The differential replay harness (what makes autonomy possible)

Goal: run the Java and C clients on identical input and compare them automatically, without a live server.

1. **Recording.**
   - Add a recorder to the C client (behind a flag) that writes the decrypted server→client packet stream, tick boundaries and all user input to a session file.
   - Make recordings against the real server with disposable accounts: login, walking, region crossing, interfaces, combat, banking, logout.
   - The server is needed only while recording.
2. **Deterministic replay.**
   - Feed a session file to both clients through a fake in-process socket.
   - Both use fixed ISAAC seeds and a seeded stand-in for `Math.random` (anticheat camera randoms). In Java these are observation-only hooks in the isolated reference build; in C they live behind a test flag.
   - Both run headless at a fixed tick rate.
3. **Comparison.** At every tick, dump and compare:
   - the full 765×503 framebuffer;
   - key state: local player, players and NPCs, interfaces, varps, inventories, scene base and plane, camera, the menu;
   - outgoing packets.

   Report the first diverging tick per category, with a diff image.
4. **Corpus.** Use a regression corpus of session files under `client-c/tests/sessions/`. `make parity` replays all of them and prints a match matrix.

Exit: `make parity` runs unattended and produces a numeric match report for every recorded session. Until the renderer is replaced, I expect the framebuffer to diverge almost immediately; state and packet comparisons are expected to be mostly usable.

## Phase C — Faithful renderer port

Goal: pixel-exact world rendering. **This needs the user's approval** (see Decisions).

Port the following line by line from the bundled Java, replacing the depth-buffer path:

- **`Pix3D`**: integer flat, Gouraud, textured and alpha triangles, texture palettes, and lighting tables.
- **`Model`**: `draw`/`drawSimple`, priority and depth sorting, and picking.
- **`World3D` / `World`**: tile ordering, occluders, roofs/visibility, setBridge, wall/decoration draws, and shared lighting.

The existing depth-buffer renderer stays buildable behind a flag until the port matches, so the installed client never regresses.

The gates are, in order:

1. TitleOracle-style single-function oracles: triangle rasterizers on fixed inputs, `Model.draw` on real cache models.
2. Static scenes against Java's `World3D.draw`.
3. Full-frame equality on replayed sessions.

This one phase subsumes the handoff's open visual gates.

## Phase D — Close the `client.java` coverage gaps

Work through the coverage map in dependency order. Order of work:

1. Session and timers: `idleNetCycles` reconnect, the AFK timer.
2. Packets with no handler.
3. Interface component types and scripts.
4. Chat, friends, ignore and private messages.
5. Settings, sounds and music.
6. Remaining menu operations.

Each feature lands only when:

- its replay session shows Java/C agreement on state, packets and frames;
- one live scenario passes on the real server.

## Phase E — Live play and stability

Long scripted sessions on the real server: travel across regions and planes, repeated reconnects, banking/combat/skilling loops, relog persistence, memory growth and frame timing. Failures become new session recordings, which feed back into Phase B's corpus.

## Working loop (every phase)

1. Pick the highest-dependency red cell in the coverage map or the parity matrix.
2. Reproduce it: a failing oracle or replay diff first, never a description.
3. Port from the Java source. If Java, TypeScript and the engine don't settle it, add a TODO and leave the cell red.
4. Pass the oracle/replay, then `make test` (zero warnings), then `make parity` (no regressions), then a live check if it touches the network or input.
5. Checkpoint: build hash, evidence in `runs/<date>-<slug>/`, and a regenerated matrix. Update `HANDOFF.md`, `CLAUDE-HANDOFF.md` and `progress.md`.
6. Continue without waiting.

**Stop and ask only for:**
- destructive or outward-facing actions;
- ambiguity that the three sources can't settle;
- server ownership questions;
- the architectural decisions listed below.

**Reporting:** a short progress note at each checkpoint, plus the current parity matrix.

## Safety rules carried forward

- Keep a last-known-good executable in `bin/`. Candidates are tested under other names, and nothing is installed until it is verified.
- Preserve all saves, caches, content, nested repositories and prior checkpoints. Use disposable test accounts only, and snapshot and compare saves around every live run.
- No commits unless authorized (see Decisions). No pushes ever. No delegates. No Cursor/Grok audit search. No `OSRS/`, and nothing after revision 225.
- Never stop a process I didn't start unless the user authorizes it.
